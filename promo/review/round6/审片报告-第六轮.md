## 1. 总体评价

这是一支**技术交付扎实、产品信息基本属实、但商业片质感不够**的产品讲解片。

**做得好的地方：**
- 手机界面是仓库真实代码实机渲染的截图，清晰度高。
- 第四幕「一句话 → 调工具 → 出结果 → 先确认 → 自动备份」的因果链完整，是全片最有说服力的段落。
- 多处诚实标注做得难得：「界面为演示数据」「画面已加速」「需配合扩展套件」「cloudflared 另计」「输入邀请码 / 官网注册领 7 天免费试用」。
- 32 个工具名与连接器源码逐一对得上。
- 技术参数无可挑剔：1080p60，零掉帧，−14.0 LUFS，−2.6 dBTP。

**主要问题：**
1. **前 3 秒抓不住人。** 0–1s 是空黑框；1–6s 的痛点用的是桌面英文后台和监控画面隐喻，没拍出「在手机上放大老后台」的真实痛点。
2. **整片高度依赖「深色极光背景 + 玻璃卡片 + 手机模型 + 英文等宽 HUD」这一套模板。** 12–54s 几乎每个镜头都是手机模型，PPT 感和 AI 模板感重。
3. **第二幕伪终端和第四幕「谁在占网速」有可被内行识破的事实细节错误。** 伪终端里写着 uhttpd 监听 0.0.0.0、隧道协议 QUIC、路径也不对；第四幕显示的工具链算不出每台设备的实时速率。
4. **第四、五幕旁白只比音乐高 3–5 dB，有被音乐盖住的迹象。** 「低延迟」「看门狗」「托管版」「官网」在两版转写中都被听错。
5. **49.3–54.1s 有 4.8 秒画面不动、没有旁白的空窗。**

一句话结论：**能看懂、可信度基本过关，但还不到「专业商业宣传片」的水准。修完 A 级问题后，可以作为开源项目的介绍片在 B 站发布。**

## 4. 问题清单

> 每条按六要素组织：时间戳｜表现｜为什么是问题｜对整体的影响｜修改建议｜优先级。时间为主片时间，竖屏单独注明。

### S 级（严重：影响可信度或无法发布）

**无。** 没有发现虚构功能、把未实现功能包装成已实现，或严重音频故障。A2、A3 是**接近 S 的事实风险**，内行观众暂停画面时会注意到，建议按必须修改处理。

### A 级（明显缺陷）

**A1｜0.00–1.00s（延续到 6.0s）｜开头空黑框，痛点画面与旁白不对位**
- 表现：
  - 0–0.15s 一道竖向扫光，0.20–1.00s 近乎纯黑（blackdetect 测到）、只有一个空矩形框在收缩，1.00s 整帧闪白。
  - 1–6s 用桌面英文 LuCI 截图和「CAM 01 · LEGACY UI · ZOOM ×3.4 / ERR 0x1F」监控墙。
  - 旁白说的是「**手机上**管路由器，只能放大老后台」，但画面里没有手机，也没有手指缩放。
- 为什么是问题：B 站、抖音前 3 秒决定划走率。第 1 秒没有信息，1–3s 的英文小字在手机上看不清。痛点没有被「看见」，只是被「说出」。
- 影响：钩子失效，第一幕的情绪起点偏弱，后面「换一种管法」的反差也跟着变弱。
- 建议：
  - 删掉 0.2–1.0s 的空框，第 1 帧直接给痛点。
  - 用竖握手机特写（可用真实手机实拍或屏幕录制），双指放大 LuCI，误点、表格横向溢出。
  - 「没公网 IP」用一张在手机上打开「端口转发失败 / 连接超时」的画面表达。
  - 监控墙隐喻（CAM 01 / ERR 0x1F）删掉或降到背景。
- 优先级：**P1（必须）**

**A2｜20.5–28.3s｜第二幕伪终端内容与真实实现矛盾**
- 表现：放大后可读到以下内容（见 `work/crops/a2_ps.png`）：
  - `uhttpd -p 0.0.0.0:8…`、`ucode /www/cgi-bin/`、`cmcp-watchdog --30s`、`du -sh /www/panel → 2.0M`，图层标签写着「TLS · QUIC」。
  - 实际实现：`src/init.d/claude-mcp` 为 `uhttpd -p 127.0.0.1:18765 -h /www-claude-mcp`（README 安全说明：「服务只监听 127.0.0.1:18765」）；目录是 `/www-claude-mcp/…`；看门狗没有 `--30s` 参数（脚本内 `INTERVAL=30`）；隧道启动参数是 `--protocol http2`，不是 QUIC。
- 为什么是问题：0.0.0.0 意味着监听所有网卡，恰好和产品最核心的安全卖点「不开端口、只走隧道」相反。OpenWrt 用户是内行，B 站观众又习惯暂停截图，这种细节最容易被拿来质疑。
- 影响：伤害技术可信度，还会连带让人怀疑「2MB」「不用公网 IP」等真实卖点。
- 建议：
  - 按真实值重写这段终端：`uhttpd -f -p 127.0.0.1:18765 -h /www-claude-mcp`、`/www-claude-mcp/panel`、`cloudflared tunnel --protocol http2`。
  - 删掉 `--30s` 和 `QUIC`。
  - 或者干脆去掉伪终端，换成真实 SSH 截图（地址打码）。
- 优先级：**P1（必须）**

**A3｜64.6–68.2s（对话延续到 73s）｜「谁在占网速」的演示链条推不出画面上的结果**
- 表现：
  - 对话中工具标签是「调用工具 · 实时网速 · 设备列表」。
  - 回答是「书房台式机正以 86.4 MB/s 下载，占了约 92% 带宽」，右屏是「终端实时下行速率排行」。
  - 源码核查：`net_speed`（实时网速）只给「各网络接口」的速率；`device_list` 只有 IP / MAC / 主机名 / 在线状态；连接器 32 个工具里没有「每台设备实时速率」。能间接定位设备的是 `list_connections`（查看连接，含来源 IP 和流量，依赖 Clash 内核），或者 `run_command`。
  - 同一套演示数据里，首页实时下行为 78.9 Mbps，这里单台设备是 86.4 MB/s（约 691 Mbps），量级相差约 9 倍。
- 为什么是问题：官网确实宣传「谁在占网速」，能力本身不算虚构，但片中把**具体工具组合和精确到 0.1 的数值**画成了确定结果，属于「把推断包装成直接读数」。数据前后不一致，也会被细心的观众发现。
- 影响：第四幕是全片的信任核心，这里一旦被挑出毛病，其余两问也会被一起怀疑。
- 建议：
  - 工具标签改为「查看连接 · 设备列表」。
  - 回答改成能从连接数据推出的形式，例如「这会儿流量最大的是书房台式机，最近几分钟下载了约 2 GB」。
  - 右屏标题改为「按设备汇总的连接流量」。
  - 把 86.4 MB/s 统一换算到与首页 78.9 Mbps 同一量级，或者干脆不写速率。
  - 加一行小字「需扩展套件运行」。
- 优先级：**P1（必须）**

**A4｜54.0–74.0s、82.6–87.7s｜旁白与音乐过近，可懂度存疑**
- 表现：分轨实测人声比音乐 RMS 只高 3.2–5.6 dB（第四幕），82.6–87.7s 只高 2.8–4.0 dB，而第一至三幕是 7–16 dB。主片和竖屏两次转写都把「低延迟」听成「第一延迟」，把「看门狗」听成「看门口」，「托管版」听成「拖管版」，「官网」听成「关网」。
- 为什么是问题：第四、五幕恰好是功能高潮和行动号召（网址），需要最清楚的人声。常见的商业混音习惯是人声高出音乐床 8–12 dB 左右；本片在关键段远低于这个水平。
- 影响：观众用手机外放（B 站、抖音的常见场景）时，可能听不清关键词和网址。
- 建议：
  - 54–74s、82–88s 的音乐床整体再降 4–6 dB，或改用 3–4 kHz 频段的动态 EQ 给人声让位。
  - 把侧链闪避从 −5 dB 加深到 −8~−10 dB。
  - 网址口播放慢 10%，前后各留 0.2s 空隙。
  - 改完再转写复核，看「低延迟 / 看门狗 / 官网」是否被正确识别。
- 优先级：**P1（必须）**。主观部分「待用户试听确认」

**A5｜49.3–54.1s｜4.8 秒静止空窗**
- 表现：两台手机（PWA / 安卓）的构图从约 48.5s 起几乎不动（帧差均值 0.17–0.21），旁白 49.28s 结束，54.10s 才重新开始。50–52s 混音 RMS 约 −29.5 dB，是全片除片尾外最低的一段。
- 为什么是问题：90 秒短片里，近 5 秒「无新信息、无旁白、无动作」相当于主动请观众划走，正好卡在第三幕到第四幕（AI 卖点）的转场前。
- 影响：节奏塌陷，第四幕的「推高」也失去了蓄力效果。
- 建议：
  - 把空窗压缩到 ≤1.5s。
  - 或者在这段放一个真实动作，例如安卓 App 里切到第二台路由器，画面上的路由器名称跟着变。
  - 或者用 1 秒黑场加音乐 riser 做「呼吸」，再硬切进第四幕。
- 优先级：**P1（必须）**

**A6｜12.2–54.0s、74–82s｜手机模型重复 + 模板化科技 HUD，PPT 感和 AI 感重**
- 表现：
  - 第二、三幕几乎每个镜头都是「深色极光背景 + 玻璃卡片 + 浮空手机模型」，景别和运动方式高度一致（慢推、轻微倾斜）。
  - 第一、五幕叠加英文等宽伪遥测（WAN 100.64.23.18 · CGNAT / LOAD 0.21 / UPTIME 12d 04h / WATCHDOG · 4/4 SIGNALS HEALTHY / AUTO-HEAL · LOG）。
  - 85.25s 粒子连线聚合成 logo，63.3s、66.2s 有镜头光斑球。
- 为什么是问题：这是当前 AI 生成科技片最典型的视觉语汇，观众会一眼归类为「模板片」，削弱「真实开源产品」的定位。
- 影响：A 维度失分的主要来源，也直接推高了「AI 味」。
- 建议：
  - 至少加入 2–3 个**真实**镜头：真实路由器实物特写（指示灯）、真人手持手机在客厅或书房操作、真实 Claude 网页窗口的屏幕录制（加速并打码）。
  - 英文伪遥测删掉一半，保留的改成中文且与功能相关。
  - 粒子聚合 logo 改成图标简单「点亮」或遮罩揭示。
  - 光斑球删除。
- 优先级：**P2（强烈建议）**

**A7｜竖屏 60s｜关键文字被裁切、字幕压 UI、收尾过紧**
- 表现：
  - 竖屏 2.25–3.25s 错误弹窗标题被裁成「IP 缺失，无法远程连接」，「公网」二字出画。
  - 9–14s 手机只占画宽约 1/3，中段大面积空白。
  - 26.25s 流量图左缘出画，字幕「点两下就行」压住柱状图标签。
  - 37.75s 字幕「问它谁在占网速」压在状态卡「低延迟线路 01」那一行上。
  - 46.75–54s 标题折行，「提醒」单独成行（孤字），伪遥测叠在标题后面，[03]、[04] 日志卡互相重叠。
  - 末句「…com」在 59.4s 才结束，音乐 0.5s 内淡出，落版只停约 2s。
- 为什么是问题：竖屏是抖音、视频号、小红书的主力格式，这些问题在手机上都会被放大。
- 影响：竖屏版完成度明显低于主片。
- 建议：
  - 第一幕错误弹窗改为竖屏专用排版。
  - 手机模型放大到画宽 70% 以上。
  - 字幕区域固定在画高 78–86%，UI 卡片避开这个区域。
  - 标题改两行等长断句。
  - 末句提前约 1.5s，结尾留 ≥1.5s 落版静帧和音乐收尾。
- 优先级：**P1（竖屏发布前必须）**

## 6. 声音评价

**旁白（3.5/6）**
- 优点：
  - 稿件口语化，「给孩子的平板设个定时断网，点两下就行」「让它给书房电脑固定个 IP」这类句子有具体场景。
  - 字幕由 TTS 词级时间生成，字幕和口型的同步精确。
  - Claude 读作「克劳德」，保证了读音统一。
- 问题：
  - 语速和语调全片恒定（rate +4%、pitch −2Hz，没有分段变化），缺少强调和停连设计。
  - 字母逐读（u h t t p d / M I T / 网址）机械。
  - 第四、五幕的误听可能来自 TTS 吐字和音乐遮蔽两方面。
- 局限：音色是否「一耳 AI」、「低」「狗」两个字是否含混，**待用户试听确认**。

**背景音乐（2.0/4）**
- 结构有设计：0–12s 暗夜脉冲 → 11.8s Sub Drop 接产品亮相 → 54s 推高进入 AI 段 → 82s 再推高进入行动号召，情绪递进合理。
- 但音色全部来自 numpy 合成（kick / hat / pluck / pad），和声是最常见的 i–VI–III–VII，缺少真实乐器的质感和动态。
- 结尾快速淡出、没有终止。

**音效（1.5/2.5）**
- 落点精确，对位清楚。
- 但 102 个音效在 90s 里过密，第四幕三次同构；「每个 UI 动作都配一声」接近 Mickey-mousing（音效机械跟随画面）。
- 建议删掉 30–40%，只保留关键交互（发送、确认、成功）和段落转场。

**混音与母带（1.5/2.5）**
- 母带达标：−14.0 LUFS 适合 B 站、抖音；TP −2.6 dBTP 有余量；零削波；LRA 4.3 保留了段落起伏。
- 主要问题是第四、五幕人声与音乐只差 3–5 dB（A4）；50–52s 出现 −29.5 dB 的空洞（A5）。
- 竖屏版同为 −14.0 LUFS、−2.4 dBTP、零削波，末尾 0.5s 淡出过急（A7）。

- **产品名与界面中使用「Claude」及近似品牌色**：是否符合商标使用规范待核实。

## 8. 修改建议

### 必须修改（发布前）

1. **A2 伪终端改为真实值，或删除**：127.0.0.1:18765、`/www-claude-mcp`、`--protocol http2`，去掉 `--30s` 和 QUIC。

## 9. 最终发布建议

- **是否建议正式发布？**
  - 当前版本**不建议作为正式商业宣传片发布**（66 分，有 7 项 A 级问题，其中 A2、A3 是可被内行识破的事实细节）。
  - 修完「必须修改」1–7 项后，**可以作为开源项目的介绍片在 B 站发布**。
  - 竖屏版在 A7 修复前不建议上抖音或视频号。
- **是否建议重新制作部分镜头？** 建议重做：
  - 0–6s（开头痛点）；
  - 20.5–28.3s 伪终端图层；
  - 64.6–68.2s 占网速问答；
  - 49.3–54.1s 空窗；
  - 竖屏第一幕和第五幕的排版。
  - 其余以调整为主（混音、措辞、防碰撞），不需要推倒重来。
- **哪些镜头应该保留？**
  - 54.5–58.3s 32 工具墙；
  - 58.75–73.8s 第四幕双屏问答（修 A3 后）；
  - 28.75–44.3s 真实面板三机位、流量图、定时断网；
  - 11.25–12.25s「O」字穿越转场；
  - 86.5–90s 落版。
- **哪些镜头最值得优先修改？** 按优先级：20.5–28.3s（A2）→ 64.6–68.2s（A3）→ 54–74s 与 82–88s 混音（A4）→ 0–6s（A1）→ 49.3–54.1s（A5）。
- **如果只能修改三个地方：**

  2. **第四、五幕把旁白抬出来（A4）**：音乐床降 4–6 dB 或加深闪避，网址放慢读，保证功能高潮和行动号召听得清。
  3. **重做前 3 秒（A1）**：删掉空黑框和整帧闪白，第 1 帧就是「手机上把老后台放大再放大」的真实痛点画面，决定 B 站和抖音的留存。
